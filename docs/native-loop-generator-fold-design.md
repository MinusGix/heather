# One loop generator, one image-facts path — design

Status: **agreed and landed 2026-09-30 (the round after the structured-lowering
round); probe V1 §2, as landed §3.5.** Owners: `issues/nat-loop-generator-as-record.md` and
`issues/read-loop-code-length-by-evaluation.md`. Builds on
`docs/native-wc-design.md` §4 (the record loop), §4.8 (the state process) and
§9 (`wc -l` on the state process).

## 1. What is duplicated

Two generators feed one process (`lib/elf64_read_state.hthr`):

- `generate_elaborated_loop_x86` (`loop_native.rs`) takes a Nat or Bool carry
  and has its own thirteen-register placement. It places the carry with the
  library's `loop_in(R, loop_nat_rep)` and bounds it with `loop_fits`. The
  step's payload and discriminator come out of one read region.
- `generate_elaborated_record_loop_x86` (`loop_record.rs`) takes a record
  carry and updates its fields in place, one piece per field. It emits the
  placement (`_rep`), the invariant (`_fits`) and the process facts they need
  (`_rep_moves`, `_room`).

Because the Nat generator's placement and invariant are the library's, the
process carries Nat-only lemmas (`count_rep`, `count_framed`,
`count_initialised`, `count_room`, `count_word`). `read_count_runs` and
`read_count_print_runs` are stated against them, where the fields profile
takes the generator's facts as parameters.

Separately, `--read-loop` and `--print` prove their code's length by
evaluating the spelled code's `len()`, which walks every byte of every
generated piece. `--fields` proves it over open parts
(`read_fields_code_len`) and instantiates it with each piece's
`_byte_length` lemma, so `image_facts` has two paths.

## 2. Probe V1: a scalar under the record lowering

The record generator was given scalar carries (§3.1), and both loops of
`examples/function-ir/readonly-loops.hthr` were generated by each generator
at the same head registers. Both certify under both.

| loop | Nat generator | record generator |
|---|---|---|
| `count_occurrences` (Nat) | 238 bytes | 228 bytes, checks about a tenth faster |
| `first_match` (Bool) | 241 bytes | 324 bytes, checks about a fifth slower |

The count loop, which is `wc -l`'s shape, gets smaller. The search loop grows
because the record path computes the payload and the discriminator as
separate pieces, and in `first_match` both read the same comparison. Search
is a test client only, so the fold takes that cost. Sharing a comparison
between the two pieces is a lowering question, left for when a program needs
it.

## 3. The fold

### 3.1 One generator

`generate_elaborated_loop_x86(elab, prefix, source, &NativeLoopPlacement,
advance: Option<&str>)` is the record generator, renamed.
`NativeLoopPlacement` takes the record placement's shape (head registers,
`fields`, `scratch`). A Nat or Bool carry is a state of one field, and that
field is the state itself: every spelling of field `i` of a state `s` goes
through one `field_of(s, i)`, which is `s.f` for a record and `s` for a
scalar. The advance theorem is required when a Nat field exists. For a
scalar Nat, its one component is the client's `LoopAdvancesByAtMostOne`, as
before. The per-field typed generator observes a scalar payload directly.
`loop_native.rs` is deleted.

### 3.2 One set of process facts

`read_count_runs` and `read_count_print_runs` (and the print tail's
`StateTail`) become polymorphic in the count's placement, as
`read_fields_spec_runs` is. They take `rep`, `fits`, `framed`,
`initialised`, `room` and the count's word in R13 as parameters, and the
Nat-only lemmas at the end of `elf64_read_state` are deleted. The CLI emits
the per-program facts (`_framed`, `_init`, `_initialised`, the count words)
from one helper for all three profiles, where `read_fields.rs` wrote its own.

### 3.3 One image-facts path

`state_code_len` in `elf64_read_state` states the length of `state_code(…,
tail)` over an open loop and tail, moving `len_app` / `len_app_is` down from
`elf64_read_fields`. `read_fields_code_len` is restated through it.
`--read-loop` instantiates it with the loop's length and the exit tail's
length, and `--print` with the loop's and `count_tail`'s, whose formatter
words give their `_byte_length`. `image_facts` then always takes a length
and its proof, and the evaluating path is deleted.

### 3.4 Placements

`--read-loop` and `--print` use the fields profile's placement at one field:
the count in R13, the flag in R10, scratch R11, RAX and RDX. The state
process's head registers (`ReadStatePlacement`) are unchanged. The tests'
search and count placements move to the same shape.

### 3.5 As landed (2026-09-30)

As designed, plus the four library definitions only the old generator used
(`loop_in`, `loop_nat_rep`, `loop_bool_rep`, `loop_no_invariant` in
`function_ir_loop_trace`). The record generator's move into `loop_native.rs`
kept the old file's name and entry point, so callers changed only their
placement. The per-field generator observes a scalar payload as the payload
itself (`publication.rs`). The client theorem
`LoopAdvancesByAtMostOne` stays: it is what a scalar Nat's one component of
the advance fact is, so `wc_l.hthr` did not change. The process library no
longer takes it, because the generator's `_room` already carries it. The
test placements keep the registers `native_loop` reads (the state in R11,
the flag in R13).

## 4. Acceptance

- One loop generator; `loop_native.rs` and the `count_*` lemmas are gone.
- `wc -l` (`--read-loop`, `--print`) and `wc` (`--fields`) build and run as
  before (`native_read_loop`, `native_wc`), and every loop, process and
  refusal test passes.
- No profile evaluates its code's length.
- `scripts/perf ab --whole-tree` on the `wc -l` build: counters are reported,
  and seconds apart from them.
