Found in the datarepr v1 round (2026-08-15, docs/native/datarepr-design.md §1.4 as-landed note 7): `value.fold` on a record value is claimed by the builtin vector receiver method before the receiver's type is consulted, so a record field named `fold` is unreachable by projection. Resolution order should consult the receiver's type first (or at least prefer a field when the receiver is a record). Workaround in the datarepr elaboration: reach through the generated namespace instead of projecting. Related: [[datarepr-separation]], [[theorem-field-projection-oom]].

## Log

- 2026-08-16: Narrowed and re-probed (2026-08-16, the repr-access-spellings round). The datarepr shape this was filed from does NOT reproduce at HEAD: resolve_dot consults the record-field route (lib.rs:4363) before the method desugaring the builtins live behind, so a field wins whenever the receiver's type infers, and every repr access shape infers — ListTok().fold(…), BinNat().fold(…), a hand-written record with fold/head/map fields, off a literal and off a neutral receiver, all check. What still reproduces is narrower than the title: a receiver whose type cannot be INFERRED falls through to the method path and the builtin claims the name, e.g. 'match n { Zero => b(), Succ(k) => b() }.fold(Zero)' at 'record Box { fold: (n: Nat) -> Nat }', which reports `fold` takes `(init, f)` on a vector receiver — a diagnostic that is a lie about a receiver that is not a vector. So the resolution ORDER is not the defect; the fallthrough's diagnostic is, plus the fact that a receiver which failed to infer gets no field-based explanation. Consequence for the repr work: docs/native/repr-access-spellings-design.md §1 records that neither of the two defects that forced the two-spelling split is load-bearing any more, and §3.2 keeps '.' as ordinary projection without designing around this.
- 2026-08-16: FIXED and closing. Reproduced at HEAD exactly as the narrowing predicted, then found to be one level finer than the narrowing said. The defect is NOT the fallthrough as such: every builtin vector method opens with elab_infer on its receiver, so a receiver whose type cannot be inferred can never reach one — but the ARITY test runs first, before anything has read the receiver, and it announced "on a vector receiver" about a receiver nobody had looked at. THE ISSUE'S FRAMING WAS TOO NARROW in a way worth recording, since it is what sized the fix: the lie is not gated on records at all. `match n { Zero => mk(), Succ(k) => mk() }.fold(Zero)` gets the same false message with no record in the file — a record field named `fold` is how it was FOUND, not what makes it fire — so the fix is not record-gated either. Mechanics are one shared helper (crates/elab/src/lib.rs, vec_method_arity_err beside the vector eliminators) consulted by the three arity branches that asserted vectorness: `map`, `head`/`tail`, `fold`. It takes the order the body would have taken anyway — infer the receiver; not a vector, the existing "`fold`'s receiver has to be a vector" wording (shared with elab_vec_fold rather than a second spelling); a vector, the arity message, now true; NO receiver at all (the direct spelling `fold()`, since the dot always supplies one), what a vector eliminator requires, which is a fact about it rather than a claim about anybody. `cons` is untouched and was never wrong — its receiver is the head element, not a vector, so its message never asserted one — and `cong` already inferred first. What a failed receiver gets instead is its own inference error, propagated as-is: "`match` in inference position needs a motive". That is exactly what the arity-CORRECT spelling has always given, so the two spellings no longer disagree about the same receiver, and it is the one thing here the writer can act on — supply the motive and the field route projects. DELIBERATELY NOT BUILT, the issue's second half ("a receiver which failed to infer gets no field-based explanation"): with no inferred type we do not know the receiver is that record, so a field-based note would be a guess layered on a first-order failure, and the failure it would be layered on is already actionable. The resolution ORDER is confirmed again as not the defect — nothing in resolve_dot moved. Tests +3 in crates/elab/tests/records.rs §12 (the builtin path out of the record fallback): the repro plus its no-record twin plus the head-overapplied shape, all asserting the motive message AND that the word "vector" is absent; a non-vector inferrable receiver naming the receiver rather than the arity, with the zero-argument direct spelling beside it; and the negative control that the arity message still fires where it is true on a genuine `[Nat; 2]` for all three of fold/map/head — without which deleting the message outright would have passed the other two. Verified end to end through the CLI under the standing ulimit. docs/native/repr-access-spellings-design.md §1's residual paragraph marked fixed and dated, since that section is the one place a reader meets this as a live defect; nothing there moves either way. Suite 1649 -> 1652, full run on the final tree; scripts/bench --check: 18 comparisons within thresholds.
