The standing lever [[certgen-harness-cost]] has recorded twice, promoted to its own issue after the non-Nat round (2026-08-12) gave it a 6x multiplier: the certgen test family is now six binaries (certgen, certgen_emissions, certgen_nonnat, certgen_controls, certgen_cert, certgen_route1_spike), and each one independently builds an elaborator and re-elaborates the same shared prefix — lib/ir_v1.hthr's declarations plus lib/certgen_code.hthr (~42 s alone after the round) plus lib/certgen_cert.hthr — before its own content starts. That is ~6 × 45 s of identical work per full suite, and every future binary split (the recorded remedy whenever a rail nears the 300 s `ulimit -t`) adds another copy. The two levers compound against each other: splitting binaries protects the rail by paying the prefix again.

Shape options, deliberately not chosen here:
- **Serialize the elaborator state**: elaborate the shared prefix once (a build-script step or a first "fixture" binary), serialize Ψ + the elaborator's tables, deserialize per binary. Largest surface — the elaborator was never designed to round-trip, and GenDef registries / MetaDefs / solver tables all carry indices that must survive.
- **Reuse the CLI's declaration cache**: `heather check --cache-dir` already skips the kernel gate on warm declarations (~95% of these files' cost per [[wf-field-conversion-cost]]'s measurement); a shared cache dir keyed for the test harness might buy most of the win with no new serialization — but the tests drive the elaborator *library*, not the CLI, and [[cache-verdicts-omit-check-settings]] is a correctness caveat on the cache as it stands. [[warm-path-rewalks-unchanged-declarations]] bounds the warm path's own cost.
- **Merge binaries behind a longer rail**: raise `ulimit -t` for a consolidated certgen binary. Rejected twice already ([[certgen-harness-cost]]) because the cap is the OOM/runaway backstop, but recorded so nobody re-derives it.

A deliberate round per the accumulator discipline (user deferred this explicitly on 2026-08-12: "we'll have to investigate that another time"). Measurement protocol per [[perf-tracking-consistent-environment]]. Trigger: the next deliberate perf round, or the next time a certgen rail split is proposed.

## Log

- 2026-08-13: Phase 0 + design. MEASURED (per-binary wall, scripts/test -p heather-elab --test <t>, debug profile, ordinary desktop load, 2026-08-13): certgen 143.9 s, certgen_emissions 169.2 s, certgen_nonnat 97.6 s (two tests in parallel on the two test threads), certgen_controls 36.0 s, certgen_cert 88.4 s, certgen_route1_spike 0.3 s — family total ~535 s wall. Two corrections to this issue's opening claim: (1) FIVE binaries pay the shared prefix, not six — route1_spike's fixtures are self-contained snippets (its Ir is a verbatim copy, no CODE/CERT); (2) the '~45 s prefix' was right in size but wrong in attribution — a phase probe (stats::kernel_ns) puts lib/certgen_code.hthr at ~42 s of which ~41 s is KERNEL GATE time, and of THAT, ~34 s is the two 'match code' shells checked at Layer::Meta in quote.rs's elab_meta_decl_inner — a THIRD gate site the gate.rs seam never covered, so the option-2 premise ('the CLI cache skips ~95% of these files' cost') was false as stated for these files: wiring the cache at the existing seam alone bought only ~8 s/binary (measured: certgen 143.9 -> 133.3 warm). DESIGN CHOSEN: the option-2 family in the shape the issue hinted at — wire the tests through crates/cache DIRECTLY (helper with_decl_cache in crates/elab/tests/support/mod.rs; store at target/decl-cache; Elaborator::set_gate) — PLUS extending the gate seam to the meta-layer site, which is where the money was: GateItem gains layer (part of the identity: same (ty, body) at two layers is two kernel questions; the binding's layer byte was already hashed) and lands_in_psi (a meta fn registers in the meta-def table, Psi never grows — the cache must not leave a pending interface hash for the next binding to absorb, nor let the admits/accepted memo answer for a neighbour at the same Psi length; both hazards are wrong-vouch class, both now guarded and regression-tested in crates/cache/tests/end_to_end.rs). Measured after the extension: warm prefix (decl prefix + CODE + CERT) 0.76 s from ~43 s, 133 hits 0 checked. REJECTED: (1) elaborator-state serialization — largest surface, never designed to round-trip, and the cache shape gets the same win at declaration granularity with no new serialization; (2) driving the CLI as a subprocess — the tests need the elaborator state in-process afterwards; (3) the longer rail — stays rejected per [[certgen-harness-cost]], not re-derived. CORRECTNESS: staleness keyed exactly as the CLI cache keys it — content-addressed interface-closure hashes (changed lib file/prelude/elaboration output => every downstream key moves => miss) plus KERNEL_SEMANTICS over crates/kernel/src (changed kernel => store discarded loudly on open). DEFAULT_FUEL lives in crates/kernel/src/typing.rs, so the [[cache-verdicts-omit-check-settings]] fuel caveat is covered by the fingerprint while fuel stays a kernel constant (logged there). Suite-honesty rules on top: the gate NEVER covers generated or mutated content (sealed to NoGate before any fixture, emission or mutant — docs/testing-generated-terms.md keeps its teeth, and the perturbed-library controls kernel-check their mutants every run by construction, since a mutated declaration has a different key anyway); and certgen_emissions takes NO gate at all, the designated backstop — every full suite still contains one front-to-back kernel-checked elaboration of the shared prefix against a defect in the cache mechanism itself. Cold path: first-use populates under target/ (cargo clean = cold), no manual pre-step; concurrent finishers race the save (atomic rename, last writer wins; a lost update is a re-check next run, never a wrong answer — and cargo runs test binaries sequentially, so in practice the first cold binary warms the rest of the same run). After-numbers (cold suite, warm suite, per-binary) land in the next entry once the verification run completes.
