Filed off the in-language-map landing (2026-08-02), per the one-deliberate-round-per-session perf discipline. try_map_code_hook (crates/elab/src/quote.rs) does, at EVERY .map use site with the template registered: one CtxApp + iterated delta-transparent WHNF of the whole meta term, and one kernel infer_term of the evaluated payload to annotate the App spine. Fine at today's scale (the template is ~30 nodes and the suite is unbothered), but it is per-use work whose result is use-independent: the payload has no free locals (its context was the bare g), so the evaluated payload and its inferred type are the SAME for every use site — the CtxApp substitution only rewrites the context inside code types, which the App spine then never consults. Levers, recorded not scheduled: (1) evaluate and infer once per registered template per elaborator, cache (payload, ty); (2) have elab_meta_decl store the payload type derived from the registered statement instead of re-inferring (the CodeTm's ty field under the context substitution); (3) if templates grow letbox chains at registration time, cache post-letbox normal forms. Trigger: a file with many .map sites showing hook time in a frontend benchmark ([[frontend-benchmarks]]), or a second registered template family.

## Log

- 2026-08-02: fold_code landed (quotation-stage-artifacts): the 'second registered template family' trigger has fired. A file declaring both templates pays the per-use CtxApp + delta-WHNF + infer_term per .map AND per .fold site. No measurable suite slowdown yet (fold suite ~0.01s), so still a lever, but lever (1) — cache (payload, ty) per registered template — would now amortize across two families.
- 2026-08-02: Accumulator tick (2026-08-02, the tabulate/nth port): the hook now serves four templates and every .map/.fold/xs[i]/container-IH use site re-evaluates its template per use. The in_language_tabulate suite elaborates each fixture three times (full lib / lib-before-this-round / Rust baseline), and full scripts/test wall time is now in the ~13-minute range. Not yet the trigger — the suites are the heavy users, not checking itself — but the per-family growth the issue predicted is now measurable; next template family should re-read the cache lever.
- 2026-08-02: MEASUREMENT CORRECTION (coordinator, 2026-08-02, after the let/blocks round): the 2026-08-02 accumulator tick above records 'full scripts/test wall time is now in the ~13-minute range'. Re-measured on this machine at 861 tests / 68 suites, with all four templates registered and the tabulate suite's three-elaborations-per-fixture shape unchanged: 237s WARM, and 254s with a forced full elab rebuild (touch crates/elab/src/lib.rs, which relinks every test binary). So the suite is ~4 MINUTES, not ~13, and compilation is ~17s of it rather than the story. The ~13-minute reading was most likely wall clock taken while a parallel agent build was competing for the same cores — scripts/test caps threads, so a co-tenant inflates wall time without inflating the suite's own cost. The correction matters for THIS ISSUE SPECIFICALLY, because that number was the evidence offered for accumulator growth: at 4 minutes the per-family growth is real but the headline is not, and a round that 'fixed' a phantom 9 minutes would have measured its win against noise. The trigger stands as originally written and is NOT met: hook time has to show up in a frontend benchmark ([[frontend-benchmarks]]), or a fifth template family has to land. Method note for the next tick: measure warm AND rebuild, on an otherwise idle machine, and record both — a single wall-clock number under unknown load is not a measurement.
