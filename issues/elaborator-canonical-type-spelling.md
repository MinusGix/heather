Filed from the 2026-09-06 x86 kernel round. Exact first-difference excerpts
of the expected-vs-inferred conversion misses on the five-node
FunctionIR/x86 module showed one declared type written three ways inside one
module: fully inlined (`Σ(…)((Σ…`, 50–300 K characters), through a named
code (`El (u475^δ)`), and as a boxed code literal (`El «(«Σ…»`). Whenever two
spellings meet, the kernel unfolds and walks the larger one in the value
domain; that was ~4.6 s of the module's ~7.7 s of kernel time. The
registration boundary that leaves the x86 model types unnamed is
[[inductive-spelling-codes-nonrecursive]]; this issue is the invariant that
boundary is a special case of.

The three spellings each have an owner today: the inline lowering is what
the recognizers fingerprint (`lower_instance` is the identity the guards
anchor on — the shape-code round's deliberate choice); the named codes are
`GenDef::TyCode`/`ShapeCode`/`ArityFn` respelled site by site behind
structural guards; the boxed literal is what the code layer writes. Every
site that fails a guard silently falls back to inline, and the kernel is
where the fallbacks are paid for.

## Direction

- Decide the canonical spelling per role (statement, annotation, value,
  code payload) and make the *recognizers* see through names rather than
  the emitters guess which copy the recognizer wants — the reverse of the
  shape-code round's mechanism 3, which moved `whnf` back to the inline
  copy to keep readers spelling-insensitive.
- A checked invariant rather than a convention: a debug-only pass over an
  elaborated module that reports two spellings of one declared type meeting
  in a conversion miss (the round's `Tc::conv_ty` miss sampler, filed under
  [[perf-profile-build-target]], already produces the datum).

## What it assumes from elsewhere

- **[[wf-shape-annotation-slots]]** owns the shape-code mechanism and its
  guards. Assumed here: only that guards decline site by site today.
- **[[inductive-spelling-codes-nonrecursive]]** owns the first concrete
  slice; this issue is not a prerequisite for it.

  Release binary at 3d10b94 plus the `char`/`list` additions of this date, `--cache`, default kernel width; counts are exact and width-invariant, so only they are quoted.

  This is this issue's own group-B shape — a record component spelled `Σ[0,0](…)` on one side and `El(app(…#tycode_fn^δ; ā))` on the other (docs/closed-argument-and-parameter-domain-spelling-design.md §1) — reached from the *type argument* end rather than from a parameter domain: `Cursor<Char>(source)`, `List<Char>` and `Certified<Char, List<Char>>(…)` each instantiate the library at a record, and every conversion along the parser's spine re-derives the disagreement.

  Found while building the scannerless character calculator ([[sequence-parser-source]]). Its consequence there: the four tier bodies cost ~35 s of gate and ~290–450 k misses each where `calc_parser`'s structurally identical bodies cost 188–204, and the file needs **more than 8 GiB** cold — it passes at 20 GiB and dies at the suite's 6 GiB per-process rail, so it cannot be wired into `crates/elab/tests/showcase_calculator.rs` until this is fixed. Two spellings were tried against it and neither is the lever: moving the tier bodies from nested `match` onto the `Result` eliminators cut misses 2.9× (854 k → 291 k, and it is the better style regardless), and returning the library's `Certified` instead of a purpose-built indexed record left them flat. Threading the character *value* through `Recognized`/`Certified` rather than a placeholder `Nat` is worth 21% on the one item that does it.

  The character calculator is therefore the first consumer whose cost is dominated by this defect rather than annoyed by it, and `probes/str/p10.hthr` is a 25-line reproduction that needs no showcase.

  from one cause:

  - 27× the conversion misses of the inductive-token control (`probes/str/p10.hthr`);
  - a peak over 8 GiB, against the suite's 6 GiB per-process rail;
  - an image 1.9× over the decode budget, hence no caching at all;
  - and therefore a 95 s warm recheck for a one-line edit, and no `--only` probe.

  The node count is the most direct measurement of the defect anyone has: it is
  the `El(app(…#tycode_fn^δ; ā))` spelling of `Char`-instantiated components
  written into every annotation, counted. It is also a cheap regression gate —
  whether `calc_text`'s image falls under 256 M nodes is a single-bit answer from
  one run, no `value-metrics` build required.
