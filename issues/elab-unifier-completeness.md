Follow-ups deferred from [[elab-stage2-metas]] (stage 2 shipped a deliberately minimal, best-effort unifier — acceptance was the level-0 Nat suite). None of these are correctness holes: the kernel re-checks every zonked term, so today's gaps surface as elaboration *errors* or kernel *rejections*, never unsoundness. Pick up when a program actually needs them.

## Deferred pieces

- **Constraint postponement.** ~~Never blocks; a checking-only argument at a meta-bearing domain is refused.~~ **Landed per-call, 2026-08-06** (docs/unifier-completeness-design.md §3–§5): checking-only explicit arguments defer behind a withheld stand-in meta and are retried after expected-type-directed solving; the general expected-type harvest subsumes the LGG hook's step 1 for every shape, and a bare polymorphic reference in checking position instantiates through the same machinery with an empty spine. The residue is **cross-call** postponement — deliberately not built (design §3.1, the per-call-world invariant). [[polymorphic-argument-with-unsolved-callee]] owns the former `compose(id, id, n)` boundary; its partial-domain instantiation handles that case within per-call scratch worlds. File against this issue when a program needs a cross-call constraint queue.

- **General pattern (Miller) inversion.** **Closed as a guard, 2026-08-06**: a non-identity all-vars renaming is unreachable today — established structurally (every transport composes maps that are identity on Gamma) and by an instrumented full run (1135 tests, zero non-identity reports) — so the all-vars check became equality with the weakened identity `embed(Gamma, d)`, which is exactly the condition under which verbatim-take-plus-`strengthen_tm` *is* the inversion. The permuted-renaming inversion is specified for the day it is reachable (design §6.3), not built: code with no reachable input is an unstated assumption with extra steps.

- **Level-meta inference.** Stage 2 does no level unification (every Nat-suite level is 0). This is *correctly* sequenced late, not merely skipped: non-cumulativity means no <= constraints exist, and universe polymorphism is layer-m only, so level inference is unification over count/adjust normal forms (Level::normalize is the oracle) that only bites once layer-m / modal programs appear. See [[elaborator-design]] (level-metas-as-L-vars) and [[frontend-roadmap]].

## Trigger

Whichever comes first: (a) a surface program whose implicit args cross-depend or use a non-identity scope, or (b) the layer-m / universe-polymorphic work where level metas become load-bearing. Until then the best-effort unifier is sufficient and kernel-gated.

## Log

- 2026-07-24: Second motivation for postponement, from [[goal-holes]]: holes are checking-only, and `apply_implicit` elaborates a callee's *explicit* arguments in inference mode (it needs their inferred types to drive unification). So `sym(?p)` is refused today and the user must write `@sym(a, b, ?p)` — a visible ergonomic dent on the most natural spelling. Postponement fixes it directly: with the argument's elaboration deferred until the domain's metas are solved, the hole gets a meta-free expected type and becomes an ordinary goal. A cheaper partial fix exists if postponement stays out of reach — check the hole against the parameter domain whenever that domain contains no meta occurrence — but it needs an occurs-style traversal over kernel Type/Term that the elaborator does not have and should probably not grow on its own.
- 2026-07-26: surface-polymorphism grew unify_ty from Id-congruence-only to full structural congruence over the formers the lowerings build, with binder-depth tracking, a strengthening test on candidate solutions, and the El rule (El ?A vs T solves ?A := code_of T). Contract unchanged: it never fails, it only learns. The concrete limit it leaves is an implicit FUNCTION parameter -- 'theorem cong_at<A, B>({f: A -> B}, {a: A}, {b: A}, p: a = b): f(a) = f(b)' declares and kernel-checks, but cong_at(p) cannot solve f, since p's type mentions a and b and not f. That is higher-order pattern unification and is this issue's, not that round's.
- 2026-07-27: The cong-with-implicit-f item recorded in the 2026-07-26 log is MISFILED and moves to [[congruence-by-anti-unification]]. That log called it 'higher-order pattern unification and is this issue's'; it is neither. '?f a =? X' is flex-rigid with 'a' an arbitrary TERM rather than a distinct bound variable, so it is outside the Miller fragment by construction and genuinely ambiguous ('?f 0 =? Succ(0)' is solved by both 'lambda z. Succ(z)' and the constant 'lambda z. Succ(0)') -- finishing this issue's pattern-inversion bullet does not approach it. The stated reason was also beside the point: nobody expected the PROOF to carry f, and in checking position the information is in the EXPECTED TYPE, recovered by anti-unification (least general generalization) rather than unification. This issue keeps postponement, general pattern inversion and level-meta inference, all of which remain correctly scoped.
- 2026-08-04: A slice landed from the form-A-at-declared-indices round (2026-08-04, narrative on [[indexed-families]]): infer_ctor now solves an indexed/forded constructor's type parameters when a CHILD argument determines them (lib.rs ctor_from_child — no unification: the child's inferred type is the family, re-applied at the written result index via FordedFam::ty_at / IndexedFam::el_at), and ctor_at accepts a written instantiation for indexed families (Leaf<Nat>), the nullary constructor's only escape. The remaining boundary, now precise: (1) a parameter occurring only UNDER a field's type constructor (xs: [A; n]) still needs real unification; (2) route 1's APPLICATION-side gap measured — len<A>(n, v: V<A>(n)) applied to VCons(…) cannot solve A because unify_ty finds nothing structural in route 1's El(elim …) family form, while 2b's Σ form unifies. Both are this issue's postponement/pattern-inversion territory.
- 2026-08-04: Measured while building the frontend bench suite ([[frontend-benchmarks]]): a POLYMORPHIC FUNCTION passed as a first-class argument at a monomorphic function type does not elaborate. Minimal repro — 'fn id<A>(x: A) -> A { x }  fn app1(f: Nat -> Nat, n: Nat) -> Nat { f(n) }  fn probe(n: Nat) -> Nat { app1(id, n) }' — dies as 'the kernel rejected `probe`: LevelMismatch'. The same shape through compose<A,B,C> fails identically; app1(succ1, n) with a monomorphic succ1 is fine, so it is the instantiation of `id`'s A in argument position, not the higher-order application. Two complaints in one: (1) it fails, which looks like this issue's level-meta-inference bullet (the elaborator picks a level for the instantiation and the domain wants another) rather than pattern inversion; (2) it fails as a bare kernel LevelMismatch with no elaborator-level message, which is a diagnostics dent on a shape a user would consider ordinary. Found because a meta-heavy bench fixture wanted 'pass id to something' and could not have it — meta/nested-inference nests pair/fst/snd instead.
