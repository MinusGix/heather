# Issues

Repo-local issue tracker: one markdown file per issue, frontmatter for metadata,
`INDEX.md` generated by `scripts/issue`. Optimized for grep/Read access (Claude)
and CLI browsing (human).

## File convention

Filename: `<slug>.md` (kebab-case, stable — it's the link target).

```markdown
---
title: Short imperative title
status: open          # open | blocked | closed
thread: T1            # optional; work thread (see THREADS section below if/when we add one)
labels: [kernel, ir]  # optional
blocked-by: [other-slug]  # optional; slugs of blocking issues
code: crates/kernel/src/term.rs:120 @ 980b47e  # optional; path:line @ commit
created: 2026-07-22
updated: 2026-07-22
---

Body: problem statement, then iterative notes appended under `## Log` with dates.
Link related issues as [[other-slug]].
```

- Code references are `path:line @ shorthash` — resolve with `git show <hash>:<path>`.
- History of an issue: `git log --follow issues/<slug>.md`.
- Closing keeps the file (set `status: closed`); it stays greppable.

## Ownership (added 2026-07-27, after a tracker review)

Three rules, each written against a failure that had already happened.

**1. An issue asserts only what it owns.** Everything else is a link naming
the *one* assumption it makes on that owner. A restated fact is a copy, and
the copy is what goes stale — [[indexed-families]] restated three facts about
`[T; n]` and was wrong about all three within a day of being filed. Prefer:

```markdown
## What it assumes from elsewhere
- **[[other-issue]]** owns X. Assumed here: only that <one specific thing>.
```

`scripts/issue show` prints `Referenced by:`, and `close`/`log` print the same
list, so changing an issue tells you who was depending on it. That is the loop
that makes rule 1 pay off; without it, links are write-only.

**2. The narrative of a round belongs to the issue that did the work.** A
meta/roadmap issue logs *one line* — what moved, and a link — plus any decision
it genuinely owns (sequencing, for a roadmap). [[frontend-roadmap]]'s log had
grown to 3,400 words re-telling rounds that each had their own issue *and*
their own doc, and its body had drifted against its own log.

**3. An issue closes when its scope is done; residue gets an owner first.**
"Still open for a follow-on" is how an issue becomes permanent and how work
becomes unfindable. If closing is blocked by deferred items, file them (or
point at an existing issue, or record that a *decision* owes nothing) and then
close. Both [[surface-records]] and [[surface-universe]] had landed in full and
stayed open for exactly this reason.

Two checks worth running by hand, since `scripts/issue check` does not:
open issues whose last log says LANDED/DONE, and open issues nothing links to.

## CLI

```
scripts/issue list [--status S] [--thread T] [--label L]   # table of issues
scripts/issue show <slug>                                  # print one issue
scripts/issue new <slug> --title "..." [--thread T] [--labels a,b] [--body-file F]
scripts/issue close <slug> / reopen <slug>
scripts/issue log <slug> < entry.md                        # dated entry under ## Log
scripts/issue log <slug> --body-file entry.md              # same, named file
scripts/issue log <slug> "note"                            # short entries only
scripts/issue threads                                      # per-thread status counts
scripts/issue check                                        # lint links/blocked-by/index
scripts/issue index                                        # regenerate INDEX.md
scripts/issue setup-git                                    # once per clone: INDEX.md merge driver
scripts/issue serve [--port 8765] [--open]                 # read-only web viewer
```

`serve` (page: `scripts/issue-web.html`, stdlib server, localhost only) is for
the human view of the whole tracker: facet filters over status and labels, an
**Areas** overview per label, and a **Graph** of `[[links]]` and `blocked-by`
edges with a focus-on-neighbourhood mode. The detail pane shows links in both
directions. It re-reads `issues/` on every request and the page reloads itself
when a file changes, so it can stay open while rounds edit the tracker. Filter
and selection state lives in the URL hash, so a view can be bookmarked.

Mutating commands (`new`, `close`, `reopen`) update `updated:` and regenerate
`INDEX.md` automatically.

**`INDEX.md` merges itself.** `.gitattributes` gives it the `issue-index` merge
driver (`scripts/issue merge-index`), which merges the index per issue rather
than per line: each line is a function of one issue's frontmatter, so taking
whichever side changed each issue's line, and re-rendering the headers and
counts, is exactly what `index` would print over the merged issue files. It
runs under merge, rebase, cherry-pick and stash alike. It leaves the index
conflicted only when both sides changed the *same* issue's line differently,
which means that issue's file has conflicted as well: resolve it, then
`scripts/issue index`. Git only knows the driver once it is registered in the
clone's own config, so run `scripts/issue setup-git` once per clone (Claude
Code sessions do it through the repo's `SessionStart` hook); an unregistered
clone falls back to the ordinary text merge. `check` still reports a stale
index, as the backstop.

**Prose goes in on stdin, not in argv.** A log entry is markdown with `code
spans`, and a shell expands backticks inside a double-quoted argument: on
2026-09-16 an entry lost three spans that way and was committed before anyone
noticed ([[issue-log-text-through-stdin]]). So `log` reads the entry from stdin
when no positional text is given, `--body-file <path>` (or `-`) is available on
both `log` and `new`, and the inline forms remain only for short entries with no
metacharacters in them. A multi-line entry is indented into its list item,
fenced blocks included, so heredocs are the normal way to write one:

```
scripts/issue log <slug> <<'EOF'
First line becomes `- <date>: …`.

Continuations are indented two spaces.
EOF
```
