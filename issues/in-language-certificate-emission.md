Research direction from the transcriber round's user review (2026-08-11), sharpening certgen-transcriber-in-language-design sec. 5's 'two futures' into three routes with a lean.

**What is unstatable today, precisely:** a code type whose statement mentions the transcriber's own output — Code(. |- Converges($prog, $env, $body, $out)) where those are meta-level LOCALS holding computed Ir/Prog values (ordinary first-order inductive data; it is only their address that is wrong — a meta fn's scope, not Psi). Code types index only by globals (the map round's correction 1, ch. 04 CAPP). So in-language we can compute the program but not state the theorem about it; proof-text emission stays Rust.

**Route 1 — Psi-staging (the lean).** The restriction is 'globals only', and the emitted text ALREADY declares the prog/Ir as definitions. So stage: elaborate those declarations first (they become Psi globals), then a layer-m builder states Code(. |- Converges(prog^delta, ...)) legally and folds the existential kit IN CODE by recursion over the Ir value. Kernel-side this looks ready — eliminators are layer-generic (typing.rs 518-583) so Ir-recursion at layer m should check, and Code/box formation is meta-only anyway (typing.rs 630/657, verified 2026-08-11), which is where the builder lives. Missing is SURFACE: ordinary match/recursion in a meta body (meta-body-statement-loop territory) and staged elaboration order (a generator that emits declarations, then emits code referencing them). Crucially this KEEPS the certifying trust story: every output individually kernel-checked, the generator free to be wrong. Verification items for whoever opens this: (a) elim over a lowered (Wf) inductive at Layer::Meta actually checks; (b) a quote payload may reference the just-minted prog^delta at the needed layers; (c) the kit lemmas are quotable at their statement types.

**Route 2 — the fold as a lemma.** One Converges-by-induction-over-Ir theorem with well-formedness hypotheses; generated certificates become applications; prog-extension-lemma retires with it. Flips CERTIFYING into VERIFIED: extending the fragment then extends a proof rather than a heuristic. Cheaper per output (the ~9s double-j kit folds stop being re-derived), costlier per feature. A charter decision on certifying-generator, not a technical default.

**Route 3 — dependent code types over meta data.** Meta-level Pi over terms indexing code — the calculus currently has no form of it at all. Heaviest, metatheory-grade; also the route that gives analyzers scrutinee-indexed motives (code-variable-analysis-api's far rung). File the kernel round only if routes 1-2 both prove insufficient.

Related: [[certifying-generator]] (owner of the staged list), [[prog-extension-lemma]] (retired by route 2, orthogonal to route 1), meta-body-statement-loop (route 1's surface prerequisite).

- 2026-08-11: The certifying-vs-verified articulation, from user discussion (2026-08-11), recorded as position: the regimes differ only in where the universal quantifier sits; the soundness gap between heuristic and proof is ZERO by construction (the certificate is the claim, about the actual artifact) and the only real gap is STATEMENT-VS-INTENT — hence the design principle this discussion minted: per-pass certificates with SMALL, inspectable statements, never one leap with one page-long statement (datarepr's refinement ladder is this principle applied). Certifying is load-bearing because compilation-to-good-code is search, and untrusted search over checked witnesses is what lets the search be aggressive. On route 3's decidability: the implementation already lives with semi-decision (fuel-bounded conversion), so the practical danger of CMTT is not hard-to-decide but SUBTLE-TO-SPECIFY equality under pending substitutions — a soundness risk, not a speed one.

- 2026-08-12: Round A LANDED (2026-08-12, managed round; docs/certgen-cert-expression-design.md@4acf2fe, lib/certgen/certgen_cert.hthr). The certificate-expression datatype is in the library: Cert (one constructor per kit lemma, except letcall_conv gets TWO -- CIh vs CCall is the fold's real decision, induction hypothesis vs callee invariant, and a constructor is what makes it perturbable in one edit) plus CertOut (CPlain / CRec with one letmatch_conv per Nat arm), and ordinary program-layer fns cert_body/cert_chain fold the transcriber's Ir into it -- full recursion at layer p, no match code, no rec_ga gate, the file carrying six of its own refl pins (ih routing, foreign routing, the no-ih decline, con chaining, the arm split, the non-rebinding decline). The split, stated once in design doc sec. 3: the library owns STRUCTURE (lemma choice, chain order, ih/foreign routing, arm split, every decline -- CStuck at the rim, recognized at readback like TNo/SigNo); Rust owns every NAME (program name, spec spellings, gih/gk/tail, callee conv-names), with spec derivation moved out of chain_from_rir entirely to the renderer. Invocation needed NO analyzer slot: cert_body is a Psi global, so run_cert_fold is an ordinary u^delta application under the same Reader budgets -- cheaper than the slot machinery and no MetaDef staleness to handle. Byte-identity confirmed by before/after diff on all five emissions including mul's re-derived add_gen_conv_in_mul; the perturbed-fold control (cert_rebind rebinding at slot 1) is refused first by the library's own theorems, then, stripped, by the kernel at the emission's invariant. Arms are selected via the library's own pick_arm -- the very function letmatch_conv's hypothesis is stated against -- so lemma and fold agree by construction. Two memo corrections recorded in the design doc: the spike's 'datatype and its renderer in lib/' overstated -- the renderer stays Rust, names being its whole remaining content; and the transcriber design's sec. 5 row 3 splits (the certificate's STATEMENT was blocked, its STRUCTURE never was).
