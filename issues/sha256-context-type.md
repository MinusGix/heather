SHA-256's state is a `List<u8>` and a length word passed side by side through every function of `lib/native/crypto/sha256_block.hthr` and `sha256_stream.hthr`, with its layout (hash value at byte 0, working variables at 32, schedule or block at 64, count at 320) as numbers in the bodies. Minus's question (2026-11-12): should the context be its own type with these as functions on it. Yes, and what stands between is listed here so each part can be done where it belongs.

What the source should read as:

```heather
record Sha256 { hash: Array<u32, 8>, block: Array<u8, 64>, fill: u64, count: u64 }

runtime fn Sha256::update(mut self, message: Bytes) { for byte in message { self.push(byte) } }
```

What is in the way, each its own issue:

1. **A record has no runtime layout** unless it is one word (`datarepr`, [[runtime-repr-narrow-words]]): "`P` has no runtime layout under the reflected fragment". The context needs a record laid out over a span of bytes, which is the views work ([[source-buffers-as-views]], [[rt-fixed-arrays-and-tables]]).
2. **A span is two parameters.** `Bytes` as one value that carries its length would halve every signature here and in the lexer, and is what makes "a span is two of six words" ([[function-call-past-six-words]]) bite less.
3. **A measured recursion cannot be a method** ([[decreases-self-parameter]]), so the loops could not be `Sha256::…` even with the type.
4. **Words are 64-bit only.** The round functions mask to 32 bits by hand; with `u32` values they would be `Sha2`'s own `big_sigma0` and the rest, and "the compiled function is the specification" would be nearer a statement than a proof ([[runtime-repr-narrow-words]], [[bitvec-rotates-and-wide-ops]]).
5. **The round constants are a tree of sixty-four leaves** because compiled code has no table ([[rt-fixed-arrays-and-tables]]): 190 of the block module's lines.
6. **Eight working variables do not fit a call**, so they live in the span and a round is three functions ([[function-call-past-six-words]]).

A step that needs none of these, taken first: the two modules respelled with what the language already has (`u64`/`u8`, numerals, `+ - << >> & |`, `if a < b` outside the loops, `mut self` methods for the stores), which a probe shows the generator takes. The loops' hand proofs go with [[decreases-word-measures-by-hand]], exclusive or with [[bitvec-xor-complement-symbols]].

Done when: `crates/linked`'s SHA-256 is compiled from a module whose functions are methods of a context type, with no layout offsets in their bodies.

- 2026-11-12: The three pieces asked of other threads merged (#583 word measures, #584 measured recursion in methods, #585 `⊕`, `~`, `42u64`), and the modules on PR #551 use what they give: the eight loops lost their `on ?dec1` blocks (assembly unchanged, `scripts/linked` reports every row unchanged) and the round's exclusive ors are `⊕`. Probes on the merged tree for what is still in the way of methods: a loop as a `mut self` method is refused because a tail branch cannot update the receiver ([[mut-self-tail-branch-receiver]], item 3's successor), and `if i < 64` as a loop's test is the generator's refusal ([[runtime-fn-if-word-proposition]]). The record itself (item 1) is untouched. Order for the context round: the tail-branch lowering, then loops as `List<u8>::…` methods with no `Mutated`/`.after` threading, then the nominal one-span record, then the length travelling with it.
- 2026-11-12: Also found respelling the round: `~e` and `e.rotr(6)` are refused in a `runtime fn` ([[rt-complement-and-rotate]]), so the round keeps `e ⊕ 0xffffffff` and the shift pairs.
- 2026-11-12: Item 3 is done and the modules use it (PR #551): every function of `sha256_block` and `sha256_stream` that stores is a `mut self` method on the span ([[mut-self-tail-branch-receiver]]), the loops test with `if h: i < 64` (#586) and `sha256_push` with `if fill = 63`, and no body threads `.after` by hand. `scripts/linked` reports every row unchanged, so the respelling is the same programs. What is still a function, and why: the four exported entry points (`sha256_compress`, `sha256_init`, `sha256_update`, `sha256_finish`) open with `let mut ctx = ctx;` and end in `Mutated(ctx, value)`, because `heather compile-x86 <file> <function>` and `EXPORTS.tsv` take an ASCII identifier that is at once the source name, the label, the file's stem and the Rust declaration (`symbol_ok`, `crates/cli/src/native.rs`): a method's export needs a symbol given apart from its name (`Sha256::init` as `sha256_init`), which is the nominal type's round and a naming choice. Also met: a non-recursive method that ends in another span method's call is taken apart and rebuilt, which the generator accepts, where the bare call is refused (its end rule wants `Mutated(span, value)`, a `Bool` match of such, or the function's own call); and a measured span loop whose test is a plain `if i < 64` with no `h:` is refused for having no `ext` companion ([[measured-span-loop-plain-if]]). Next here: the nominal type over a span (item 1), a proposal for Minus since it is surface: a `datarepr` whose representation is a span and its length word (the route `SInt(64)` took over a word, [[runtime-repr-narrow-words]]), against a transparent alias, against staying on `List<u8>`.
- 2026-11-12: Probes for the nominal type, on PR #551's compiler. (a) A transparent definition, `def Hash: Type = List<u8>;` with `fn Hash::zero(mut self ctx: Hash, …)`: the methods elaborate, and inside them `ctx.put_within(…)` and `ctx.zero(…)` resolve, but a local written `let mut ctx: Hash = bytes;` does not find `ctx.twice(…)` ("unbound name `twice`"), so the namespace does not stay with the value, and the generator refuses the parameter ("`Hash` has no runtime layout"). Not the route. (b) A record, `record Hash { bytes: List<u8> }`: `ctx.bytes.put_within(…)` is refused, a field not being a place ([[field-path-places]]), before the generator is reached. So the order for the nominal type is: field paths as places (language, a parser lowering); a record over a span in the generator (its `datarepr`, the route `SInt(64)` took, or the reflector reading a one-field record); a method's export under a symbol; then the length with the span and the fields laid over it (items 1 and 2).
- 2026-11-12: Decided by Minus (2026-11-12): field paths "definitely" (built, [[field-path-places]]), and the context type goes straight to laid-out fields, "we're going to want them very soon regardless". Layout is to be easy to use on its own, "similar to how Rust's layout api works", so that it can be computed at run time too, "but ideally better with proofs". So the order is: a layout library of ordinary values (size, alignment, field offsets, with their theorems), then a record laid over a span that the generator reads through it, then a method's export under a symbol. The one-field `datarepr` stepping stone is dropped.

- 2026-11-12: Words as compiled code, proved to be the codec's (PR #551). `sha256_word_at` and `List::sha256_put_word` moved to `lib/native/runtime/stored_words.hthr` as `List::u32_be_within` and `List::put_u32_be_within`, with `u64_be_within` and `put_u64_be_within` beside them (the count's accessors are now those at byte 320).   The projection laws for reads are in `stored.hthr` (`get_then_fst`, `get_then_snd`, `get_padded`, `get_map`, `get_array_nth`): the probes prove this context's count to be `Stored::u64_be().get(bytes, 320 + at)` and schedule word `i` to be `Stored::u32_be().get(bytes, i * 4 + (64 + at))` from the record's codec, by the laws and not by unfolding.

  Left for this issue: the generator that publishes, per field, the offset, an accessor that is a stored-word function at that offset, and the projection law instantiated, so that no offset is written in a body; the projection laws for stores; then the context as a record a `runtime fn` holds (`docs/layout-design.md` §6.2, stage B).
- 2026-11-12: 2026-11-12, PR #551: the context is a record over its span, on the statement side. `lib/std/machine/part.hthr` has fields as values: a `Part<A, B>(whole)` carries its offset, its codec, what it is of the whole (`of`), the whole with it replaced (`with`), and two laws (`reads`, `frames`), and parts are made by combinators proved once (`fst`, `snd`, `element`, `then`, `field`). `lib/native/crypto/sha256_context.hthr` is `record Sha256 { hash, working, schedule, count }` with its codec and one part per field and per word, written by hand as the `laid` generator will write it. The offsets in SHA-256's bodies are theorems by `refl` (`Sha256::schedule_at`, `count_at`), and each access by compiled code is tied to the record by one application of a `stored_words` theorem (`Sha256::schedule_put`: the store leaves `Sha256::of(ctx) with { schedule = vector_update(…) }`; `Sha256::count_is`: the stream's count is the record's). - 2026-11-12: **Offsets by name, built (round 1 of `docs/layout-design.md` §9.5, PR #551).** No body of `sha256_block` or `sha256_stream` writes a field's offset as a number any more: `laid record Sha256` publishes `Sha256::hash_at`, `working_at`, `schedule_at` and `count_at` as words, the two modules import `sha256_context` and add to them (`(i << 2) + Sha256::schedule_at`), and the context dropped `order := AsWritten`, so where its fields lie is the declaration's choice. The module order turned round with it: the record and its theorems come first, and the two facts about the stream's own accessors (`Sha256::count_is`, `put_count_is`) moved to `sha256_stream`.

  What it needed below: a generator could not get a number out of the layout library, because the host's `Whnf` is out of budget on `Nat::round_up` at two digits. The host has a new request, `Numeral` (`docs/host-elaboration-interface-design.md` §28), which runs a closed `Nat` term in the value domain, and `laid` asks it for each part's offset and publishes the literal.

  What Rust is told: `SHA256_CONTEXT_BYTES` and `SHA256_DIGEST_AT`, numerals of the module held to the record by `refl` theorems and generated into `crates/linked/generated/constants.rs`. The wrapper lends that many bytes and reads the digest there; `block::CONTEXT` is now the whole context (it was the 320 bytes before the count).

  The four SHA-256 exports were recompiled and certified, with the same stack lines; their assembly changed, because `Sha256::working_at + 16` is an addition of two constants at run time and `i + Sha256::hash_at` adds zero until the IR folds them ([[function-ir-pass-arithmetic-folds]]). The linked crate's tests pass on the new bytes.

  Left of "no layout offsets in their bodies": a word's place within its array is still arithmetic in the body (`Sha256::working_at + 16` is the fifth working variable). That goes when a body reads `ctx.working[4]`, which is stage B's held terms (§9.2, round 3).
